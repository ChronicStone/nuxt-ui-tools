## Scope

- Step(s) worked on:
  - Step 3. Schema Builder
  - type-system parity and inference hardening
- Goal for this session:
  - fix `context` / `pageContext` inference regressions
  - propagate sort-key generics consistently from the source through table and grid schema
  - close more of the V1 schema parity gaps without moving into new runtime work

## Work Completed

- rebuilt the schema generic flow so `defineTableSchema(...)` derives filter and sort key types from the source instead of opportunistically inferring them from arbitrary schema values
- fixed `context` and `pageContext` extraction helpers so they merge all declared items into the resolved object type instead of collapsing to a weaker single-item shape
- expanded context item typings toward the V1 contract:
  - `loader`
  - `query`
  - `views`
  - `condition`
- tightened source and schema type defaults so sort-related APIs now default to row key paths rather than plain `string`
- threaded sort-key generics through:
  - source request context
  - serializers
  - table columns via `sortableKey`
  - table `defaultSorting`
  - grid `defaultSorting`
  - grid sorting options
- expanded grid schema typing so it now exposes both:
  - `sorting`
  - `sortOptions`
  while preserving the current draft behavior
- added stronger schema-builder type tests covering:
  - field/composite render params
  - resolved `context`
  - resolved `pageContext`
  - table default sort assignability
  - grid sorting option assignability

## Decisions Made

- treat sort/filter key inference as a source concern, not a whole-schema inference concern
- keep improving V1 parity inside the type layer before taking on more runtime implementation
- support both `grid.sorting` and `grid.sortOptions` in the type surface for now so the draft API can evolve without losing consumer compatibility
