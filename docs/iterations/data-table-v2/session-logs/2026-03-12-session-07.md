# Session Log

- Date: 2026-03-12
- Session ID: 07
- Agent: Codex

## Scope

- Step(s) worked on:
  - Step 3. Schema Builder
  - schema API decisions and type-surface cleanup
- Goal for this session:
  - align filters with row-property targeting instead of column targeting
  - make `column.field(...)` fully property-backed
  - inject typed field `value` into `column.field(...).render(...)`

## Work Completed

- replaced filter `columnId` semantics with property-targeting `key`
- constrained property-backed filter keys to row field paths in:
  - static filters
  - dynamic filter builders
  - filter definitions
- updated `column.field(...)` so it is now explicitly property-backed:
  - no `sortableKey`
  - `sortable` remains available
  - `render(...)` receives a typed `value`
- kept `column.composite(...)` as the derived-column escape hatch with typed `sortableKey`
- added `TableFieldValue<TRow, TField>` and threaded it into field render params
- updated the playground schema to exercise the new contracts:
  - static filter uses `key`
  - property-backed filters point to real row fields
  - `column.field('name', ...)` now renders from typed `value`
- expanded the field-column callback contract so row-aware callbacks also receive the full row plus typed field value:
  - `render(...)`
  - `cellProps(...)`
  - `colSpan(...)`
  - `rowSpan(...)`
  - `labelRowSpan(...)`
- updated type tests to cover the new field-render value inference

## Decisions Made

- filters target row properties, not columns
- property-backed filter keys should infer from the row shape
- `column.field(...)` is not a partially-derived column type; it is the canonical property-backed column and therefore owns its sorting target implicitly
- explicit `sortableKey` remains only on derived columns such as `column.composite(...)`
